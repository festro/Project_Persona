# H2 Bridge Design -- taskboard.py <-> Hermes native kanban

Date/time: 2026-06-13 0204 PDT
Author: Claude (with Brandon)
Status: DESIGN (pre-implementation). No code landed yet.
Convention: ASCII only; dated doc (docs/h2_bridge_design_YYYYMMDD_HHMM.md).
Scope: Phase 8 H2. Decides HOW the persona's Task Board and Hermes' own kanban
cooperate, then sketches the wiring so the EVO-X2 implementation session is fast
and low-risk. Architecture choice (BRIDGE, not native-only) was set by Brandon
2026-06-13; this doc fills it in.

--------------------------------------------------------------------------------
1. DECISION RECAP
--------------------------------------------------------------------------------

H2 had an open fork: ride Hermes' native kanban as the only board, or keep
taskboard.py and BRIDGE the two. Decision: BRIDGE.

- taskboard.py (data/tasks.db) + the persona API /jobs stay the CANONICAL board
  that the persona surfaces to its user. It is the source of truth for "what work
  exists for this persona."
- Hermes' kanban is the EXECUTION substrate for work the persona delegates to an
  agent worker. Hermes owns execution-lifecycle truth for a delegated card while
  it runs; the bridge mirrors that truth back into taskboard.py.
- A thin, one-process bridge keeps the two consistent. No re-plumbing of either
  board's internals.

Why bridge over native-only: the persona API, /jobs, taskboard.py, and the
offline test suite already exist and are validated; the persona must surface a
single board to its user regardless of who executed the work. Native-only would
mean re-pointing the persona at Hermes' DB and re-proving all of that. The bridge
is additive and reversible.

--------------------------------------------------------------------------------
2. THE TWO BOARDS, SIDE BY SIDE
--------------------------------------------------------------------------------

2.1 Persona Task Board (ours) -- services/api/taskboard.py

- Storage: single SQLite file, data/tasks.db (TASKS_DB env). Stdlib sqlite3, WAL.
- Schema: one table `tasks` (job_id TEXT PK, status TEXT, state TEXT = merged JSON
  blob, created_at INTEGER, updated_at INTEGER). task_set() merge-upserts a patch;
  task_get/ task_list/ task_delete/ count round it out.
- Lifecycle today: NONE that is claimable. POST /agent/run writes the job row at
  status="running", runs tools/taskman2.py inline via asyncio.to_thread (300s
  timeout), then sets status to "ok" | "error" | "timeout". There is no
  "queued"/"ready"/"claimed" state because nothing external pulls work -- the
  endpoint executes the job itself.
- Read surface: GET /jobs (list, limit) and GET /jobs/{job_id}.
- Job payload: the taskman2.py job JSON (task_id + the job spec).

2.2 Hermes kanban (theirs) -- NousResearch/hermes-agent v0.16.0

- Storage: per-board SQLite. Default board ~/.hermes/kanban.db; named boards
  ~/.hermes/kanban/boards/<slug>/kanban.db. (We set HERMES_HOME -> the persona
  profile dir, so the effective base is the profile dir, NOT ~/.hermes -- CONFIRM
  the resolved kanban.db path on EVO-X2; see Open Questions.)
- Columns / lifecycle: Triage -> Todo -> Ready -> In progress (running) ->
  Blocked -> Done. Canonical lifecycle truth: ready -> running -> blocked / done /
  archived. Dependency promotion auto-moves todo -> ready when parents finish.
- Tables (per docs): task_runs (per-attempt: outcome, summary, metadata, log_path,
  exit code, started/ended) and task_events (every transition: promoted, claimed,
  heartbeat, completed, blocked, gave_up, crashed, timed_out, reclaimed,
  claim_extended). Retry history is first-class (one row per run).
- Dispatcher: on each tick (60s default, or "Nudge"/`hermes kanban` immediate) it
  claims a ready task and spawns the assignee profile as a worker process
  (`hermes -p <assignee> chat -q <prompt>`), passing HERMES_KANBAN_TASK / _DB /
  _BOARD / _WORKSPACES_ROOT / _WORKSPACE / _RUN_ID / _CLAIM_LOCK / HERMES_PROFILE /
  HERMES_TENANT in the env. The worker drives the card with kanban_* tools.
- Worker terminators (exactly one per run): kanban_complete(summary, metadata) ->
  done; kanban_block(reason) -> blocked (respawns on kanban_unblock); or the
  process exits without a tool call -> crashed / gave_up / timed_out.
- Resilience the dispatcher already provides: stale-claim TTL (15 min, but a live
  PID gets the claim extended, only a dead PID is reclaimed), crash detection via
  kill(pid,0), circuit breaker (kanban.failure_limit, default 2; per-task
  --max-retries), per-task max_runtime_seconds, stranded-in-ready diagnostics.
- Surfaces (all route through the same per-board DB): dashboard (:9119), CLI
  (`hermes kanban create|show|runs|watch|unblock|decompose|tail`, most with
  --json), and the worker kanban_* tools. The dispatcher also writes per-task
  stdout/stderr to <board-root>/logs/<task_id>.log.

2.3 The shape mismatch that the bridge must absorb

- Ours is "run inline, record result." Theirs is "queue, claim, run in a separate
  process, record runs + events." The bridge adds a DELEGATED lifecycle to our
  board so a job can mean "handed to Hermes, awaiting its result" instead of "ran
  here."
- Ours is a single merged-state row; theirs is task + runs + events. The bridge
  collapses Hermes' rich run/event history into our state blob (keeping the full
  detail as nested fields + a pointer to the Hermes task id and log path).

--------------------------------------------------------------------------------
3. STATE / FIELD MAPPING
--------------------------------------------------------------------------------

3.1 Status mapping (Hermes -> persona taskboard `status`)

  Hermes task/run state        Persona taskboard status
  --------------------------   ------------------------
  (bridge just created card)   delegated      (NEW)
  ready / todo / triage        delegated
  running (run outcome=active) running
  done (run=completed)         ok
  blocked (review-required)    blocked        (NEW)
  blocked (gave_up breaker)    error
  run=crashed                  error
  run=timed_out                timeout
  run=spawn_failed             error   (transient; only surfaced if terminal)

  NEW persona statuses introduced by the bridge: "delegated" and "blocked". These
  are additive; existing /agent/run inline jobs keep using running|ok|error|
  timeout untouched. The offline suite asserts the existing set, so adding values
  (not changing the existing ones) keeps it green; add explicit assertions for the
  two new values.

3.2 Field mapping

  Persona job state blob field     Source / meaning
  ------------------------------   --------------------------------------------
  job_id (PK)                      our correlation key; created by the bridge
  kind = "hermes_delegate"         marks the row as bridge-owned (vs agent_run)
  hermes_task_id                   id returned by `hermes kanban create --json`
  hermes_board                     board slug (default: "persona" or "default")
  status                           per 3.1
  delegated_at / started_at /      unix ts; mirrored from task_events
    finished_at
  summary                          from kanban_complete summary (done)
  metadata                         from kanban_complete metadata (changed_files,
                                     decisions, tests_run, ...)
  block_reason                     from kanban_block reason (review-required: ...)
  hermes_log_path                  task_runs.log_path on EVO-X2 (for deep audit)
  last_event_seq                   high-water mark for idempotent event replay
  attempts                         count of task_runs seen

3.3 Payload mapping (persona delegate -> Hermes card)

  `hermes kanban create "<title>" --assignee <profile> --tenant persona \
     --priority <n> --body "<spec>" --json`

  - title/body: from the persona delegate request (a short title + the work spec;
    the spec is the human-readable instruction, NOT the taskman2 JSON -- Hermes
    workers are LLM agents, not taskman2 runners).
  - assignee: a Hermes profile name = a persona "role". For H2 start with the
    existing safe `default` profile as the sole assignee; add role profiles
    (e.g. researcher, writer) later. The assignee MUST resolve to a profile or the
    card sits in ready with skipped_nonspawnable.
  - tenant: "persona" so the whole bridge namespace is filterable on the board.
  - back-reference: put our job_id into the card so a human reading the board can
    trace it -- via a leading body line "persona-job: <job_id>" and/or an initial
    kanban_comment. (We do NOT rely on parsing it back; the binding of record is
    hermes_task_id captured at create time -- see 5.)

--------------------------------------------------------------------------------
4. SYNC ARCHITECTURE
--------------------------------------------------------------------------------

4.1 Transport choice: CLI/JSON + event watch (NOT direct DB writes)

Recommended: the bridge talks to Hermes through its PUBLIC surface --
`hermes kanban create --json` to enqueue, and `hermes kanban watch
--kinds completed,blocked,gave_up,crashed,timed_out --json` (plus `hermes kanban
runs <id> --json` / `show <id> --json` for detail) to learn outcomes. Writes back
into OUR board via taskboard.task_set (in-process import, same as the API).

Rationale:
- The docs are explicit that all mutation flows through kanban_* tools / CLI /
  dashboard, never raw DB writes from outside. Writing kanban.db directly would
  couple us to internal schema (task_runs/task_events) that can change between
  Hermes versions and would bypass the dispatcher's invariants.
- Read-only DB peeking is tolerable as a diagnostic fallback, but the event watch
  + runs --json is the stable contract. Treat raw-DB reads as best-effort only.

Rejected: registering taskboard.py/taskman2 as an external CLI worker LANE (so
Hermes dispatches INTO our runner). The lane contract exists (spawn_fn is
pluggable) but the docs flag it as "not yet a paved path" with per-integration
glue still required (exit-code -> kanban_complete/block mapping, workspace env
mapping, auth). That inverts the chosen direction anyway (we want the persona to
delegate OUT to Hermes agents, not Hermes to drive our taskman2). Revisit only if
we later want Hermes to farm work onto the persona's own executor.

4.2 Process + placement

- One bridge process, `tools/hermes_bridge.py` (stdlib + the project's existing
  deps), running ON EVO-X2 -- because Hermes is Linux/WSL2-only and lives on
  EVO-X2, and the persona stack (API :8000, llama :8090) also runs there. The
  whole bridge is therefore LOOPBACK/local to EVO-X2: no new network egress.
- It needs in-process access to taskboard.py (point TASKS_DB at the same
  data/tasks.db the API uses) and `hermes` on PATH with HERMES_HOME set to the
  persona profile dir (so it shares the agent's safe-config + board).
- Lifecycle: for H2 a standalone long-running loop is fine (systemd-style or
  `manage.py` foreground). Later it folds in as a Phase 3 daemon child next to
  nats-server / llama / api (the EventBus can carry delegate requests then).

4.3 Two flows

FLOW A -- delegate (persona -> Hermes), enqueue:
  1. A persona job is marked for delegation (new endpoint POST /agent/delegate, or
     an /agent/run payload with kind="hermes_delegate"). The API writes the row at
     status="delegated" with the spec; it does NOT run taskman2.
  2. The bridge sees the new delegated row (poll task_list or subscribe to a small
     queue), checks state.hermes_task_id is unset, and calls
     `hermes kanban create ... --json`, capturing the returned id.
  3. task_set(job_id, {hermes_task_id, hermes_board, delegated_at}). Card is now in
     Hermes ready; the dispatcher claims + runs it on its next tick.

FLOW B -- mirror (Hermes -> persona), outcome:
  1. The bridge tails `hermes kanban watch --json` for the persona tenant (or polls
     `runs --json` for the set of open hermes_task_ids).
  2. On each event past last_event_seq it maps the state (3.1) and merges into our
     row via task_set: running on claimed; ok + summary/metadata on completed;
     blocked + block_reason on blocked; error/timeout on the terminal failure
     outcomes. last_event_seq and attempts advance.
  3. The persona surfaces the row through the existing GET /jobs and /jobs/{id} --
     no persona-side change needed beyond understanding the two new statuses.

4.4 Human-in-the-loop on "blocked"

When a Hermes worker review-blocks (reason prefixed "review-required: "), our row
goes status="blocked" with block_reason. The persona surfaces it for the user. To
resume, a persona action (new POST /jobs/{id}/unblock, optional for H2) tells the
bridge to run `hermes kanban unblock <hermes_task_id>`; the dispatcher respawns the
worker, which sees the prior run's block reason in its worker_context.

5. IDEMPOTENCY & CORRELATION
--------------------------------------------------------------------------------

- Binding of record: our job_id <-> hermes_task_id, captured the instant `kanban
  create --json` returns and stored in our state blob. The bridge NEVER creates a
  second card for a row whose state.hermes_task_id is already set (create is gated
  on its absence). If the create call returns but the process dies before
  task_set persists, the row stays "delegated" with no hermes_task_id; on restart
  the bridge would re-create -> a duplicate. Mitigation: write an intent marker
  (status stays "delegated", set a `delegate_inflight` ts before the create) and,
  on restart, reconcile by listing Hermes tasks in tenant=persona whose body
  carries the matching "persona-job: <job_id>" line before creating a new one.
- Event replay safety: task_set is merge-idempotent (re-applying the same status
  is a no-op in effect), and last_event_seq guards against re-processing the same
  task_event. Mirroring is therefore safe to run at-least-once.
- Crash/restart: the bridge is stateless beyond the two SQLite boards. On boot it
  (a) reconciles "delegated"+inflight rows against Hermes tenant listing, then
  (b) resumes the watch from the max(last_event_seq) across open rows.

--------------------------------------------------------------------------------
6. EGRESS POSTURE
--------------------------------------------------------------------------------

- The bridge adds NO new network surface: kanban.db, the persona API, and Hermes
  all sit on EVO-X2; the bridge speaks to them locally (sqlite file + local CLI +
  127.0.0.1 API).
- Delegated WORKERS inherit the per-profile safe-config (H1: tools.disabled +
  API-key-gating + terminal.backend=local + browser.allow_private_urls=false +
  disabled_toolsets) because the dispatcher spawns `hermes -p <assignee>` under the
  same HERMES_HOME the bridge sets. CONFIRM the spawned worker inherits HERMES_HOME
  from the bridge's environment (Open Questions).
- This is still only the config-time half of containment. The runtime half (H1.6
  kernel netns/iptables + daemon env hygiene) remains a separate, still-required
  task and is NOT closed by H2.

--------------------------------------------------------------------------------
7. FAILURE HANDLING (who owns what)
--------------------------------------------------------------------------------

- Worker crashes / OOM / timeout / spawn_failed: Hermes' dispatcher handles retry,
  reclaim, and the circuit breaker. The bridge only mirrors the terminal outcome;
  it does NOT implement its own retry. This is a feature of choosing bridge --
  Hermes already has the hard parts (TTL, kill(pid,0), failure_limit).
- Bridge down while Hermes runs: no harm; Hermes keeps executing and recording
  runs/events. On bridge restart, section 5 resync catches up the missed events.
- Persona API down: delegated rows persist in data/tasks.db; the bridge can still
  mirror outcomes into the file, and /jobs reflects them when the API returns.
- Hermes down: delegated rows stay "delegated"/"running"; nothing is lost. When the
  gateway/dispatcher comes back it resumes from kanban.db.

8. IMPLEMENTATION PLAN (H2 sub-steps)
--------------------------------------------------------------------------------

H2b -- persona side: add status values "delegated"/"blocked" awareness + a
       delegate entry point (POST /agent/delegate or kind on /agent/run that
       writes the row WITHOUT running taskman2). Offline tests for the two new
       statuses + the delegate write path. No live model needed.
H2c -- bridge: tools/hermes_bridge.py with create (Flow A) + watch/mirror (Flow B)
       + reconcile-on-boot. Unit-test the status map + correlation logic with a
       faked `hermes` CLI (stub that emits canned --json) so it is provable
       off-mount, mirroring the taskboard harness style.
H2d -- EVO-X2 live wire: set HERMES_HOME -> profile dir, ensure the `default`
       profile is a valid assignee, run the dispatcher (gateway or kanban daemon
       headless), delegate one real task end to end, confirm the persona /jobs row
       transitions delegated -> running -> ok with the Hermes summary attached.
       Confirm worker egress posture live.
H2e -- docs: changelog + roadmap H2 -> partial; knowledge.md gets the bridge in the
       architecture section; handoff.

Gates: H2b/H2c are off-mount provable now. H2d is the EVO-X2 live gate (the real
Exit-Gate evidence for "Hermes claims a Task Board task, executes it, writes
results back").
