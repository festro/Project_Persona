# WSL H2 Simulation Runbook -- everything-in-WSL

Date/time: 2026-06-13 0311 PDT
Author: Claude (with Brandon)
Status: RUNBOOK (for the WSL staging run before EVO-X2 migration).
Convention: ASCII only; dated doc.
Scope: stand up the WHOLE stack (llama + persona API + Hermes + bridge) inside WSL2

================================================================================
0. CONFIRMED FINDINGS (sandbox dive into hermes-agent v0.16.0 @ 9b1e0d6f)
================================================================================

These resolve most of the design doc's open questions; the runbook bakes them in.

- KANBAN DB LOCATION. The kanban board is SHARED ACROSS PROFILES by design.
  `kanban_home()` resolution: HERMES_KANBAN_HOME (if set) -> else
  get_default_hermes_root(), which when HERMES_HOME is `<root>/profiles/<name>`
  returns `<root>` (the parent), NOT the profile dir. The default board's DB is
  `<root>/kanban.db` (back-compat path); named boards are
  `<root>/kanban/boards/<slug>/kanban.db`. HERMES_KANBAN_DB pins the file directly.
  => For the bridge + dispatcher to agree deterministically, PIN it: set
  HERMES_KANBAN_HOME (or HERMES_KANBAN_DB) in BOTH the dispatcher and the bridge env.
- CLI --json SHAPES (what hermes_bridge.py consumes):
  * `kanban create --json` -> the bare task dict: {"id", "title", "body", "assignee",
    "status", "priority", "tenant", "created_at", "result", ...}. The bridge reads .id.
  * `kanban show <id> --json` -> WRAPPED: {"task": {<task dict>}, "latest_summary":
    str|null, "parents": [...], "children": [...], "comments": [...], "events":
    [{kind, payload, created_at, run_id}], "runs": [{id, profile, step_key, status,
    outcome, summary, error, metadata, worker_pid, started_at, ended_at}]}.
    NOTE: task fields are under "task"; "runs" is TOP-LEVEL; there is NO "block_reason"
    or "log_path" key. A blocked task's reason is in the blocked run's summary/error
    (or latest_summary). tasks.result is usually null -- handoff text is the latest
    run summary. hermes_bridge.derive_update() already matches this.
- TASK STATUS SET: triage, todo, scheduled, ready, running, blocked, review, done,
  archived. run OUTCOMEs: active, completed, blocked, gave_up, crashed, timed_out,
  spawn_failed. The bridge maps both (review -> blocked, done/archived -> ok, etc.).
- DISPATCHER (headless): `hermes kanban dispatch` runs ONE pass (reclaim stale,
  promote ready, spawn workers). Continuous = `hermes gateway start` (embedded
  dispatcher, 60s tick). The standalone `--daemon` flag is DEPRECATED. For a
  controlled sim, loop `hermes kanban dispatch`; for hands-off, run the gateway.
- WORKER SPAWN: the dispatcher runs `hermes -p <assignee> chat -q <prompt>`. The
  assignee MUST be an existing profile or the card sits in ready
  (skipped_nonspawnable). Worker env carries HERMES_KANBAN_TASK/_DB/_BOARD/
  _WORKSPACE/_RUN_ID, HERMES_PROFILE, HERMES_TENANT.

STILL TO CONFIRM LIVE (need a running Hermes + model, hence this runbook):
  (a) the spawned worker inherits the profile safe-config (egress off) in practice;
  (b) gateway headless footprint (does it demand messaging creds?); (c) sane
  max_runtime_seconds / failure_limit for delegated work.

================================================================================
1. TOPOLOGY (everything in WSL)
================================================================================

  WSL2 Ubuntu
    |- llama-server  :8090  (Qwen3.6, Vulkan or CPU)        <- persona model
    |- persona API   :8000  (services/api/server.py)        <- Task Board + /agent/delegate
    |- hermes        (env_hermes)                            <- kanban + dispatcher + workers
    |- hermes_bridge.py                                      <- delegated rows <-> kanban

All on ONE Linux filesystem -> data/tasks.db and kanban.db are both native (no /mnt
9p SQLite-locking risk). The bridge talks to the board in-process (taskboard.py) and
to Hermes via the CLI. Loopback only.

================================================================================
2. PREREQS
================================================================================

- WSL2 with Ubuntu 22.04/24.04. `wsl --install` / a recent distro.
- A NATIVE-FS clone of the repo inside WSL (recommended: ~/Git/Project_Persona),
  NOT /mnt/d/...  -- SQLite WAL over the 9p /mnt boundary is unreliable, and the
  build/venv are faster on the native fs. Sync via git:
      git clone <your remote> ~/Git/Project_Persona
  (or `git clone /mnt/d/Projects/Git/Project_Persona ~/Git/Project_Persona` then set
  the remote). Keep committing on Windows; pull into WSL.
- After clone, restore exec bits (lost across some copies):
      chmod +x ~/Git/Project_Persona/scripts/*.sh ~/Git/Project_Persona/*.sh

================================================================================
3. INSTALL (one shot)
================================================================================

The updated installer does the uv-editable Hermes flow + the services venv + the
llama.cpp build. From the repo root in WSL:

    cd ~/Git/Project_Persona
    AI_ROOT=$PWD bash scripts/setup_native_stack.sh

Useful env toggles:
- CPU_ONLY=1            build llama.cpp without Vulkan (simplest in WSL; slower).
- SKIP_HERMES=1         skip the env_hermes install (if you only want the persona side).
- HERMES_REF=<sha>      pin a different hermes-agent commit (default 9b1e0d6f).
- WITH_TORCH_EMBED=1    add the sentence-transformers extra (default lean fastembed).

Vulkan in WSL is possible (Mesa + the WSL GPU passthrough) but finicky; CPU_ONLY=1
is the low-friction path for a plumbing-focused sim. The model can also be a small
GGUF for speed -- it only needs to produce a coherent worker reply.

================================================================================
4. ENV PINNING (do this once per shell / put in an env file)
================================================================================

    export AI_ROOT=~/Git/Project_Persona
    export TASKS_DB=$AI_ROOT/data/tasks.db
    export HERMES_HOME=$AI_ROOT/persona/profiles/default
    export HERMES_KANBAN_HOME=$AI_ROOT/run/hermes_kanban
    export HERMES_CLI=$AI_ROOT/env_hermes/bin/hermes
    export HERMES_BRIDGE_TENANT=persona

Pinning HERMES_KANBAN_HOME makes the dispatcher and the bridge share ONE board at
$AI_ROOT/run/hermes_kanban/kanban.db regardless of profile. Add run/hermes_kanban/
to .gitignore (runtime state).

6. STAND UP THE STACK
================================================================================

    python3 manage.py up
    python3 manage.py status
    curl -s 127.0.0.1:8000/health | python3 -m json.tool | grep -E "delegate|task_store|status"

Expect status ok, task_store present, and the new "delegate" block.

Initialize + start the kanban dispatcher (pick ONE):

    $HERMES_CLI kanban init
    # controlled, one pass at a time (good for a sim):
    $HERMES_CLI kanban dispatch
    # or hands-off continuous (embedded 60s dispatcher):
    $HERMES_CLI gateway start

================================================================================
7. END-TO-END SMOKE (the H2d gate)
================================================================================

Delegate a unit of work (writes a "delegated" row; does NOT run taskman2):

    curl -s -X POST 127.0.0.1:8000/agent/delegate \
      -H 'content-type: application/json' \
      -d '{"job_id":"sim-001","title":"Summarize the H2 design doc","body":"Read docs/h2_bridge_design_20260613_0204.md and write a 5-line summary.","assignee":"default"}'

Run one bridge cycle (creates the Hermes card, then mirrors state back):

    python3 tools/hermes_bridge.py --once

Drive the dispatcher so a worker runs the card (loop dispatch a few times, or let
the gateway tick), running the bridge --once after each to mirror progress:

    $HERMES_CLI kanban dispatch
    python3 tools/hermes_bridge.py --once

Observe the persona row transition delegated -> running -> ok with the Hermes
summary attached:

    curl -s 127.0.0.1:8000/jobs/sim-001 | python3 -m json.tool
    $HERMES_CLI kanban show $($HERMES_CLI kanban list --tenant persona --json | python3 -c "import sys,json;print(json.load(sys.stdin)[0]['id'])") --json

PASS = /jobs/sim-001 ends status "ok" with a "summary" (and "metadata" if the worker
emitted any). Try a review-required path too: a worker that kanban_block(reason=
"review-required: ...") should land the row at status "blocked" with block_reason.

================================================================================
8. WHAT TO WATCH / GOTCHAS
================================================================================

- SQLite on native fs only. Do NOT put tasks.db or kanban.db under /mnt/d for the
  run -- WAL locking over 9p corrupts/hangs. Native ~/Git clone avoids it.
- assignee typos -> card stuck in ready with skipped_nonspawnable; check
  `$HERMES_CLI kanban diagnostics`.
- Egress check (confirm live): while a worker runs, verify it has no outbound network
  tool access (safe-config). This is open question (a) and the main thing the sim
  must prove before EVO-X2.
- If `gateway start` demands messaging creds you don't want, use the
  `kanban dispatch` loop instead (open question b).
- Line endings: ensure scripts are LF (the repo is; `git config core.autocrlf` sane).
- Bridge run modes: `--once` for a single cycle (scriptable), default loops every
  HERMES_BRIDGE_INTERVAL (30s).

================================================================================
10. WSL VALIDATION RESULTS (2026-06-13) + EVO-X2 DEPLOYMENT NOTES
================================================================================

The everything-in-WSL run validated the H2 bridge END TO END against the real
Hermes (changelog 1458; handoff 1458):
  delegate -> bridge creates card -> dispatcher claims -> spawns worker -> worker
  runs the agent (connects to persona :8090/v1) -> bridge mirrors delegated ->
  running -> error back into /jobs (attempts/started_at/finished_at all correct).

Completion (status=ok + summary) was NOT reached in WSL because the tiny 1.5B sim
model cannot drive Hermes' tool-calling loop -- the worker log showed
"Messages: 2 (1 user, 0 tool calls)" and "I'm sorry, I can't continue". That is a
MODEL-CAPABILITY floor, not a bridge defect.

Constraints learned (the first three are SIM-ONLY workarounds for the small model;
they are NOT needed with EVO-X2's 35B):
  A. default-assignee HERMES_HOME = the ROOT (dir holding profiles/), reads
     <root>/config.yaml. The profiles stage now seeds persona/config.yaml from the
     default profile so the spawned worker is configured. (Or use named profiles.)
  B. Hermes requires >=64K context on the main model AND every auxiliary; the
     profiles stage sets model.context_length + auxiliary.*.context_length=65536.
  C. PERSONA_CTX splits across PERSONA_PARALLEL; set PERSONA_PARALLEL=1 so a single
     slot holds the ~20k+ token worker prompt. (At 32768/4 = 8192/slot it 400'd.)
  D. (always) pin HERMES_KANBAN_HOME so dispatcher + bridge share one board.

EVO-X2 Exit-Gate run (the real close for H2):
  1. Stack already serves Qwen3.6-35B (>=64K ctx) -> SKIP overrides A/B/C; the 35B
     satisfies the context floor and can tool-call. Keep D (pin HERMES_KANBAN_HOME)
     and the default-profile config (A is harmless to keep).
  2. Set assignee=default (or a named role profile) pointing model.base_url at the
     EVO-X2 persona endpoint; confirm the safe-config (egress off) on that profile.
  3. POST /agent/delegate a real task -> run the bridge tick loop -> expect
     /jobs/<id> to reach status=ok with a summary (and metadata). That closes the
     H2 Exit Gate. Also confirm the spawned worker has no outbound network (egress).
  4. Then wire the bridge as a long-running service (or Phase 3 daemon child) and
     proceed to H3-H6.
